# NoteBridge 功能与工作原理说明

> 本文原先按 0.1.1 整理。0.1.3 和 0.1.4 的新增功能与变化请以 README 和各版本修复说明为准；电脑和手机的实际安装版本需分别检查。部分旧段落仅供了解原有机制。

## 1. 这个插件做什么

NoteBridge 是 Obsidian 到 Hexo 网站源码仓库之间的手动发布工具。它把发布目录里的 Markdown 笔记转换成适合网站使用的副本，收集文章引用的本地图片，经用户确认后提交到 GitHub。后续网站是否生成并更新，由仓库中的 GitHub Actions 等部署流程决定。

它的核心目标是：在保留 Obsidian 原笔记的前提下，让电脑和手机可以识别、更新同一篇已发布文章，同时尽可能避免误覆盖远端内容或因改名重复发布。

**手动发布是前提。** 修改笔记不会自动上传；预览和确认提交也不是同一件事。插件会监听本地改名和删除事件以维护记录或提示，但不会因此自动发布或自动删除线上文章。

## 2. 使用前的环境和配置

- Obsidian 最低版本为 1.11.4；插件声明支持桌面及移动端（`isDesktopOnly: false`）。是否正常使用仍取决于设备上的插件文件、权限、网络和同步状态。
- 每台设备都需要安装插件。若坚果云只同步笔记而不同步 `.obsidian`，电脑和手机必须分别安装同一版本、配置相同仓库与路径，并各自配置 GitHub 凭据。
- 插件通过 Obsidian 的 SecretStorage 读取 GitHub 密钥，普通插件设置保存的是密钥引用。GitHub fine-grained token 需要目标仓库的 **Contents 读写权限**；查询工作流还需要 **Actions 读取权限**。
- 不需要在使用设备上安装 Git、Node.js 或额外服务器。设备需要连接 GitHub。

### 主要设置

| 设置 | 默认值 | 用途 |
| --- | --- | --- |
| GitHub 仓库 | 空 | 格式为 `所有者/仓库`。 |
| 源码分支 | `main` | 接收发布提交的分支。 |
| 发布根目录 | `blog` | Obsidian 仓库中参与发布的笔记范围。 |
| 文章目标目录 | `source/_posts` | GitHub 仓库中保存文章的位置。 |
| 图片目标目录 | `source/imgs` | GitHub 仓库中保存本地图片的位置。 |
| 站点 root | `/` | 站点部署路径，用于生成图片链接。 |
| 图片公开 URL 路径 | `imgs` | 相对于站点 root 的图片访问路径。 |
| 站点地址 | 空 | 可配置站点地址。 |
| 部署工作流文件名 | `pages.yml` | 查询对应 GitHub Actions 工作流的状态。 |
| 首页排序脚本 | `scripts/index-order.js` | 可选的首页排序脚本路径。 |
| 公开 frontmatter 字段 | `title,date,updated,tags,categories,permalink` | 控制上传副本保留哪些文章属性。 |
| Fluid 文章封面和头图 | 开启 | 处理 `index_img` 和 `banner_img`。 |

以上是代码默认值，不等于你设备上的实际设置。更换仓库、分支或路径前，应先检查旧记录及两台设备配置。

## 3. 日常发布流程

1. 在发布根目录内编辑文章，将需要上传的本地图片放到该目录范围内的 `imgs` 文件夹。
2. 在文章菜单选择 **NoteBridge：预览并发布**，或通过命令面板选择 **发布当前文章**。也可以使用 **同步全部变化**，预览整个发布范围内符合条件的文章。
3. 插件读取文章、发布设置及设备间同步记录，检查文章标识、目标路径和附件，并生成一份准备上传的文章副本。
4. 在预览中检查文章路径、图片路径和上传副本。若存在问题，先修正后重新预览；还可以选择调整首页排序。
5. 点击 **确认提交此快照** 后，插件再次核对设置、记录及 GitHub 文件状态，通过检查才提交。预览时创建的快照是本次提交的内容；期间若记录或关键条件改变，需要重新预览。
6. 提交成功后，插件记录本次发布结果，并查询配置的工作流。等待笔记和 `NoteBridge同步记录` 都完成同步后，再在另一台设备编辑或发布。

“预览发布范围”用于查看，不等于提交；“同步全部变化”虽然名字包含“全部”，仍先显示预览、需要确认，并且只处理符合发布范围的文章和其引用图片。

### 哪些文章会被选中

插件扫描发布根目录下的 Markdown 文件，包括子目录；位于任何层级 `imgs` 文件夹中的 Markdown 不作为文章。如果文章属性中存在以下任一布尔值，该文章会跳过：

```yaml
draft: true
# 或 publish: false
# 或 published: false
```

不在发布根目录内的笔记不会作为发布文章。普通发布不会因为本地文件缺失而自动删除远端文章。

## 4. 文章编号、改名与防重复

### 编号是什么

预览可发布文章时，如果笔记没有编号，插件会向**本地笔记的属性（Frontmatter）**自动添加随机 `notebridge_id`，例如：

```yaml
---
notebridge_id: 0123456789abcdef0123456789abcdef
---
```

该值由插件生成；上面只是格式示例。它用于把文章与发布记录联系起来，在 Obsidian 属性区或源码模式中可以查看。它**不会被放入上传到网站的文章副本**。已有文章不会仅因安装插件就全部出现编号；要在新版插件处理该文章后才可能添加。添加编号本身会修改本地笔记，即使之后没有确认发布也可能已经写入。

请不要手动删除编号，也不要把同一个编号复制给另一篇不同的笔记；检测到重复编号时，插件会停止并要求核对。

### 改名后为什么通常不会生成第二篇

插件保存“本地文章 → GitHub 目标文件”的对应关系。已发布的文章改名或在发布目录内移动后，插件尽量通过编号、改名记录及同步记录继续对应原来的远端文件，下次发布更新原文件，而不是按新文件名创建另一份。网页最终 URL 还取决于 Hexo 的 permalink 和文章属性，不保证始终不变。

如果编号已同步到另一台设备，但对应发布记录还没到达，插件会保守停止，避免把旧文章误认成新文章。缺少可信记录、历史改名发生在旧版安装之前、目标已经存在但无法确认归属时，也不能保证自动识别，需要人工核对。

### 旧版本已经产生重复文章怎么办

打开要保留的本地文章，运行 **NoteBridge：核对当前文章的旧重复发布记录**。插件提供符合条件的旧关联，显示旧远端文章和保留文章供比较；确认属于同一篇后，可以清理旧关联。

**这个功能只清理插件的旧关联，不会删除 GitHub 文件或网站页面。** 若要删除历史重复页面，仍需单独确认具体远端文件，再进行删除和部署。

## 5. 手机与电脑如何同步

插件不负责替代坚果云同步，而是借助外部同步工具传递数据。相关内容分为三类：

| 数据 | 保存位置 | 同步方式 |
| --- | --- | --- |
| 笔记、编号与引用图片 | Obsidian 仓库内的笔记和图片文件 | 由坚果云同步。 |
| 发布记录 | 本机 localStorage，以及仓库根目录 `NoteBridge同步记录/` 下的设备 JSON 文件 | 设备各自写入，JSON 文件由坚果云同步；预览及提交前会读取合并。 |
| 插件、设置与凭据 | 各设备 `.obsidian` 和本机密钥存储 | 若不统一同步 `.obsidian`，需要分别安装配置；密钥在各设备分别设置。 |

同步记录包括仓库配置、文章和图片路径、基线等；冲突合并后还可能包括已发布的文本，**不包含 GitHub token**，但仍应按私人数据管理。记录不会作为博客文章上传。插件会按仓库、分支和相关路径区分记录；设备配置不同可能无法合并成同一组。

当多设备记录不一致时，插件会只读核对 GitHub 并尝试合并；无法确认基线、路径或日期时会停止。若电脑和手机离线同时修改同一篇笔记，坚果云仍可能产生同步冲突；NoteBridge 不会自动决定保留哪一份，应先手动处理笔记冲突并等待同步完成。

推荐顺序：设备 A 发布 → 等待笔记和 JSON 同步 → 设备 B 确认同步完成后再操作。不要在记录写入失败或同步尚未完成时切换设备继续发布。

## 6. 文章属性和内容转换

插件生成一份上传副本，不是直接把整个本地文件原样上传。默认公开 `title`、`date`、`updated`、`tags`、`categories`、`permalink`；其他属性只有在设置为公开字段且被支持时才会保留。`draft`、`publish`、`published` 和 `notebridge_id` 等控制字段不会上传。

- 没有 `title` 时，使用笔记文件名。
- 没有 `date` 时，首次准备时生成并记录日期，后续沿用记录；不会自动计算 `updated`。
- `index_img` 和 `banner_img` 按 Fluid 封面开关单独处理。
- 转换上传副本通常不改原文；但自动添加编号、保存分类或选择封面会修改本地笔记属性。
- 代码块和常见行内代码中的示例会尽量保留。复杂图片语法、引用式图片、普通 Obsidian 文章链接、笔记嵌入、HTML 图片等不在完整支持范围内，遇到无法安全处理的内容会报错停止；不支持 Dataview 渲染。以预览内容为准。

## 7. 图片、封面与头图

正文支持常见 Markdown 图片和 Obsidian 图片嵌入。本地图片需位于发布根目录内的 `imgs` 文件夹，可使用 PNG、JPG/JPEG、GIF、WebP、SVG 和 AVIF。插件解析图片、生成网站可访问的路径，并把实际引用的图片纳入本次提交；HTTP(S) 外链保持外链，不会下载。

例如，默认路径设置下，文章引用 `blog/imgs/封面.jpg` 时，插件会把图片计划提交到 `source/imgs/封面.jpg`，并在文章副本中生成相应的网站路径。子目录按插件映射规则保留，实际结果请看预览。

选择 **NoteBridge：选择封面** 可以从本地可用图片中选择首页封面、文章页头图或两者，保存到笔记的 `index_img` / `banner_img` 属性；随后仍要发布才会更新网站。选择器不直接导入外部图片，部分包含特殊字符的路径不会列出。图片缺失、路径超出范围或目标冲突会阻止发布。

**当前 NoteBridge 上传的是图片文件内容，未实现自动压缩或自动转 WebP。** 如有需要，应在导入前单独处理；网站源码仓库中已有的图片优化流程不等于插件本身具有自动压缩功能。

## 8. 分类、目录与首页排序

### 分类和目录

通过 **NoteBridge：选择仓库分类和文章目录**，插件只读扫描 GitHub 上已有文章，提取已有分类，并列出目标目录下已有的文章文件夹。分类和目录是两项独立选择：

- 分类写入当前本地笔记的 `categories` 属性，会替换原分类；需要之后发布才能影响网站。
- 目录决定首次发布时的远端目标位置，保存到插件记录；已发布文章的远端路径固定，不能通过此选择器直接移动。
- 扫描失败或仓库树不完整时不会把结果视为完整分类列表。无法解析或不在扫描结果中的分类可能不显示。

### 首页排序

发布预览中可选 **调整首页排序**。插件读取设置中指定的脚本，把文章路径加入名单并允许调整顺序；最终确认后，脚本与本次文章和图片一起进入同一次 Git 提交。脚本预览后若在远端发生变化，发布会停止。

目前只支持脚本顶层唯一的静态字符串 `order` 数组；动态表达式、数组内注释或重复路径等情况会拒绝修改。名单外文章的实际排序取决于网站脚本本身；撤回文章时不会自动清理排序名单。

## 9. 冲突检查与合并

发布前插件会比较要修改的 GitHub 文件与上次记录的基线。如果远端文件已经发生变化、目标存在但没有可信基线，或路径归属无法确认，插件会停止，避免直接覆盖。

对于已有可信基线的文章，可以运行 **NoteBridge：比较并合并当前文章的发布冲突**：

1. 读取上次发布版本、当前本地准备上传的副本、GitHub 当前版本。
2. 对三者进行逐行比较；不同位置的改动尝试合并，重叠部分用冲突标记提示手动处理。
3. 检查并编辑合并结果，移除所有冲突标记，再进入预览并确认提交。
4. 提交前再次核对远端文件和本地原文，若比较后又发生变化则停止。

合并只改变上传副本，不会自动改写本地 Obsidian 笔记。为防止下次发布丢失保留的远端内容，插件会把合并覆盖记录保存在本机和同步记录中。手工写进合并结果的新图片链接不会因此自动上传对应图片。首次发布没有可信基线、远端文件被删除、历史版本不可读取等情况不能自动接管。

更换 GitHub 密钥本身不应被当作文章版本；但如果远端内容与基线不同，仍须处理冲突。不要通过删除记录来强制覆盖。

## 10. 状态查看和撤回

### 状态面板

点击左侧 NoteBridge 图标，或运行 **NoteBridge：查看文章发布状态**，可搜索、筛选文章并查看本地状态。插件比较转换后的文章、相关图片和记录的基线；点击 **只读核验 GitHub** 可核对远端文章文件。

GitHub 核验不检查远端图片；远端文件存在也不代表网页部署成功。面板最多显示 200 篇，可缩小搜索或筛选范围。

### 工作流状态

每次提交后，插件按提交 SHA 查询指定工作流；等待中或运行中时约每 15 秒检查一次，最多持续 10 分钟。桌面显示状态栏，手机可用 **NoteBridge：查看最近提交的工作流状态** 命令。

“提交成功”表示 GitHub 接收了提交；“工作流成功”表示指定工作流成功运行；网站是否真的更新，还取决于工作流是否包含成功的构建和部署步骤。

### 撤回发布

使用 **NoteBridge：撤回已发布文章**，选择有记录的文章并确认远端路径。插件核对基线后提交删除文章文件；如果远端变化或缺乏可信记录，就停止。远端图片保留，本地笔记保留，Git 历史中的旧内容也仍然存在。

本地删除已发布文章时，插件可能提示是否撤回；这也可能由同步删除触发。关闭提示或选择保留不会删除线上文章。如果撤回后本地文章仍符合发布条件，以后“同步全部变化”可能再次发布；可将其设置为草稿或移出发布范围。

## 11. 实际提交机制和安全边界

确认后，插件通过 GitHub API 创建需要的文件对象、目录树和 Git 提交，以非强制方式更新目标分支。同批次文章、图片和可选排序修改会一起提交；内容没有变化时不会产生新提交。请求按实现节流，遇到限流不会自动重试。

写入前会检查基线、目标归属、图片冲突和配置变化；网络中断导致无法确定结果时，应先检查 GitHub 提交和文件状态，避免盲目重复提交。插件不会自动清理远端未引用的图片，也没有完整的自动发布队列、后台重试或跨设备笔记冲突解决机制。

## 12. 常用操作速查

| 想做什么 | 入口 | 会立即修改什么 |
| --- | --- | --- |
| 查看或发布当前文章 | 文章菜单 → 预览并发布 | 预览可能给本地笔记添加编号；确认后才提交 GitHub。 |
| 发布整个范围 | 命令面板 → 同步全部变化 | 先预览；确认后提交本批列出的文件。 |
| 选择封面 | 文章菜单 → 选择封面 | 保存时修改本地文章属性；不立即上传。 |
| 选择分类和目录 | 文章菜单 → 选择仓库分类和文章目录 | 可修改本地分类及保存目录记录；不立即上传。 |
| 处理发布冲突 | 命令面板 → 比较并合并当前文章的发布冲突 | 生成可编辑的上传副本；确认后才提交。 |
| 清理旧重复关联 | 命令面板 → 核对当前文章的旧重复发布记录 | 确认后修改插件关联记录，不删除远端文件。 |
| 撤回线上文章 | 命令面板或文章菜单 → 撤回发布 | 二次确认并通过基线检查后删除远端文章文件。 |
| 查看部署 | 命令面板 → 查看最近提交的工作流状态 | 只读查询，不修改仓库。 |
