# NoteBridge 评估与优化建议

评估对象：当前工作区 0.1.1；日期：2026-11-01。

**总体判断：NoteBridge 已具备清晰的个人博客发布流程，防误覆盖设计较好；当前最需要补齐的是异常后的恢复能力、发布内容的隐私边界和多设备状态模型。建议先完善手动发布，再考虑自动化。**

## 值得保留的优点

1. **产品定位明确。** 在 Obsidian 中写作，生成 Hexo 副本，手动确认后提交。最终用户不需要 Git、Node.js 或独立服务，适合个人博客和手机写作。
2. **远端写入保护扎实。** 发布前核对文件基线、归属及目标碰撞；已有同名文件没有可信记录时停止。文章、图片和可选排序脚本进入一次提交，并以 `force:false` 更新分支。基线一致且内容不变时不重复提交。见 [github.ts](D:/Log/Codex/NoteBridge/src/github.ts) 的 `publish()`。
3. **发布范围和默认元数据公开范围清楚。** 限定发布目录、附件范围、Frontmatter 白名单；内部 ID 不上传。Token 通过 SecretStorage 获取，记录文件不包含 Token。这个边界值得继续强化。
4. **已有文章身份的基础。** `notebridge_id`、旧路径映射、设备独立 JSON 记录，让改名和跨设备发布有了可核对的依据；合并不简单依赖设备时间戳，避免时钟差异决定覆盖结果。
5. **失败时优先保留内容。** 不完整远端目录树、附件缺失、未识别链接、冲突等大多会停止，不轻率猜测。后续应补恢复入口，保留这些保护。
6. **自动化测试有实际价值。** 83 项覆盖了范围判断、同名冲突、非强制提交、记录同步、合并、封面、分类和排序。它们证明已有规则可回归，但不能证明所有规则组合和真实设备时序都已覆盖。
7. **区分提交、工作流与网站更新。** 没有把 API 提交成功直接等同于网页发布成功，这个状态表达是合理的。

## 优先处理的具体问题

### 1. 隐藏注释会进入上传副本；BOM 可能绕过草稿和元数据过滤

**证据：** [core.ts](D:/Log/Codex/NoteBridge/src/core.ts) 第 29–45 行仅识别从第一个字符开始的 `---`；第 74–100 行不处理 Obsidian 的 `%%...%%` 注释。分类解析器反而已在 [categories.ts](D:/Log/Codex/NoteBridge/src/categories.ts) 第 5 行移除 BOM，解析行为不一致。

已复现：

- `正文 %%内部备注%%` 的备注原样保留在上传内容中，目录内安装的 Hexo renderer 会把它渲染为可见文本。Obsidian 官方说明 `%%` 注释在阅读视图隐藏，因此存在明确的编辑器/网站表现差异。[官方语法说明](https://obsidian.md/help/syntax)
- 向 `prepare()` 输入带 UTF-8 BOM 的文本 `\uFEFF---\ndraft: true\nprivate: ...`，它没有返回跳过，而是生成新 Frontmatter，把原属性块当正文保留。这是转换器层已确认的问题，尚不能直接推断真实设备一定会上传这样的文件。

**影响：** 发布目录不等于整篇内容都适合公开；属性白名单也不能保护被当作正文的属性。公开仓库一旦提交内容，后续删除当前文件也不能从既有 Git 历史中移除它。

**建议先修：** 所有 Frontmatter 入口共用一个解析器，统一 BOM、行尾、结束符、字段类型和解析错误处理。为 Obsidian 注释制定显式策略：默认从上传副本剔除，未闭合或无法安全识别时阻止发布；代码块、行内代码和转义符中的示例须保留。HTML 注释也应明确是否上传；仅隐藏页面显示不等于没有公开源码。预览显示“已剔除的私密内容类别和数量”，避免在日志中重复保存原文。

**验收：** 标准和 BOM 文件的草稿过滤一致；单行、多行、未闭合注释及代码示例均有样例；受保护内容不会进入任何上传 item。

### 2. 撤回没有可跨设备传播的删除记录

**证据：** [main.ts](D:/Log/Codex/NoteBridge/src/main.ts) 第 226–240 行撤回成功后删除 `targets` 和 `baselines`；[sync.ts](D:/Log/Codex/NoteBridge/src/sync.ts) 第 42–68 行把各设备仍存在的映射并入结果，再验证远端。普通撤回没有对应的 tombstone（明确记载“已撤回”的记录）。已有 `retiredSources` 用于清理旧重复关联，未覆盖普通撤回。

**复现场景：** 电脑和手机都有文章 A 的旧发布记录；电脑撤回 A 并写出自己的新 JSON；手机的旧 JSON 仍存在。下次合并时，手机的旧映射被重新纳入，而 GitHub 上 A 已删除，于是报“同步记录与 GitHub 不一致”。**等待同步完成本身不能消除另一台设备保留的旧快照。**

这不会直接把文章重新上传，但会阻塞记录同步，并影响依赖它的预览、提交和撤回。另一个独立的现有行为是：撤回后本地文章仍符合发布条件时，未来可能重新发布。

**建议先修：** 新增按文章 ID 记录的撤回事件，包括目标、被撤回的基线、撤回提交 SHA、事件 ID 和逻辑版本。合并先解释撤回事件，再处理旧快照；不要按设备时间戳简单选最新，也不要删除所有历史记录来消除报错。显式记录 `withdrawn` 状态，只有用户选择“重新发布”才转回发布状态。

**验收：** A 撤回、B 离线、旧文件晚到、重复同步、应用重启、再发布这几种排列下，文章状态保持一致，其他文章仍能处理。

### 3. 历史合并冲突缺少可用的解决入口

**证据：** [main.ts](D:/Log/Codex/NoteBridge/src/main.ts) 第 273 行把 `overlay.base`、本地转换结果、`overlay.merged` 再合并；重叠时只抛错。第 284–298 行的冲突命令先调用同一 `snapshot()`，因此也会被这个错误挡住。补充探针确认没有打开可编辑的冲突窗口。

**复现场景：** 上次发布保留了 GitHub 中对 B 行的修改，本地笔记仍是旧 B 行；后来在 Obsidian 修改同一行。普通预览停止，执行“比较并合并当前文章的发布冲突”仍停止。网站与本地的差异藏在 overlay 中，用户很难直接理解。

还有一个关联问题：[main.ts](D:/Log/Codex/NoteBridge/src/main.ts) 第 491–496 行的状态面板只比较 `prepare()` 结果，没有应用 overlay。同一篇文章的发布结果已经与基线一致，面板仍可能显示“待同步”；该现象也已复现。

**建议先修：** 将“生成本地发布表示”和“解决冲突”拆开。冲突返回包含三个版本的结构化结果，不应只有一个异常字符串；为“远端新改动”与“历史 overlay 对本地新改动”各提供恢复路径。状态面板、预览、真正提交必须调用同一个内容准备服务。

长期建议明确本地笔记是主稿。若能安全映射，提供用户主动选择的“将远端变化写回本地”以及修改预览、备份；图片 URL 和 Frontmatter 转换不可逆时，继续保留并明确展示 overlay，不要直接用网站副本覆盖笔记。

**验收：** 历史 overlay 的再次冲突可以从 UI 解决；不改本地时状态面板显示无变化；一次解决后的结果重启及跨设备后保持一致。

### 4. 改名记录以路径为中心，不能支持正常的改回原名

**证据：** [sync.ts](D:/Log/Codex/NoteBridge/src/sync.ts) 第 18 行拒绝目标路径已经出现在旧重命名键中的情况；[main.ts](D:/Log/Codex/NoteBridge/src/main.ts) 第 250 行还会阻止在历史路径创建新文章。

**已复现：** `a.md → b.md → a.md` 被拒绝。已经有稳定文章 ID，但很多记录仍以路径为主键，旧路径永久保留会限制正常重命名和路径复用。

**建议：** 逐步迁移到 `articles[id]`，路径作为 `localPath` 和 `remotePath` 属性。路径历史负责恢复线索，不永久占用名字；重命名事件使用版本关系区分“旧事件重放”和“合法改回”。旧记录保留兼容读取及迁移备份，不能一次删除旧映射。

### 5. 发布和身份注册缺少可恢复的事务

**证据：** [main.ts](D:/Log/Codex/NoteBridge/src/main.ts) 第 267–272 行先修改笔记添加 ID，再登记 ID；第 366 行先完成远端提交，再写 localStorage 和同步 JSON。第 74 行直接覆盖设备 JSON，插件层没有临时文件、校验与备份恢复协议。

已复现：初次添加 ID 的过程中有其他编辑写入正文，代码正确检测内容改变并停止，但 ID 已经进入笔记，`articleIds` 尚未登记。下一次预览又因“文章已有标识，但没有对应记录”停止。单台设备也可以出现，不一定是同步尚未完成。

另一个风险来自代码顺序：提交成功后应用退出、localStorage 保存失败或同步文件写入失败，远端与本地记账会出现时间窗口。当前能提示部分写入失败，却没有持久化待恢复操作。`github.ts` 的异常回查能确认目标提交正好是 HEAD 的情况；若远端继续前进，则保守停止。第 68 行虽然写了三次循环，但所有路径都会返回或抛错，实际没有下一轮重试。

**建议：** 在操作前持久化 journal，写入 `operationId`、配置身份、文章 ID、预期基线、目标内容哈希和阶段；创建 commit 后、更新 ref 前持久化候选 commit SHA。重启后只读核验，判断未提交、已经提交、结果不确定，并提供恢复动作。身份登记使用类似机制处理“ID 已写入但记录未完成”。同步记录采用版本、校验、备份及适配存储能力的临时文件替换；读到半写入文件时保留上一个可信版本，禁止把损坏文件当成空记录。

对外部同步工具，临时文件重命名也不意味着整个多文件同步原子完成，仍须有完整性验证和事件版本。恢复不得通过放宽基线校验来实现。

### 6. 单篇问题可能扩大为整个发布范围不可用

**证据：** [main.ts](D:/Log/Codex/NoteBridge/src/main.ts) 第 246 行在单篇发布前扫描整个范围的标识；解析出错可直接抛出。第 251 行只要存在本地缺失的已发布文章，就阻止未记录的新文章。`syncRecords()` 合并时核对所有历史基线，而不仅是本次操作涉及的文件。

例如：某篇历史文章或图片被远端修改，与它无关的新文章也可能先在同步阶段被阻止；未识别的旧记录缺失时，也没有完整“保留线上、解除本地关联”的通用恢复入口。

**建议：** 区分全局错误和文章级错误。配置损坏、ID 重复、同一远端目标被多篇占用应保留较强阻断；其他问题进入单篇状态和待处理列表。全局身份索引可持续维护，但提交前只对本次依赖闭包执行强一致核验；允许用户明确选择发布无冲突的子集，并重新生成完整预览，不能静默跳过。

## 使用体验、性能和维护方面的改进

| 现状 | 弊端 | 建议 |
| --- | --- | --- |
| Markdown-it 主要用于识别代码块，正文图片仍逐行正则替换 | 复杂语法难覆盖；普通 `[文章](other.md)` 会原样通过，最终可能指向不存在的网页；Wiki 链接又被拒绝 | 使用统一语法树/Token 层及源位置转换；定义支持、拒绝、警告三类语法。站内链接需结合明确 permalink 规则，不能仅把 `.md` 改成 `.html` |
| 预览展示所有上传副本，没有差异摘要 | 很难看出哪些文章真正变化，容易忽略隐藏内容和大图片 | 首屏展示新增/修改/撤回、字段变化、图片数量及大小，按需展开文本差异；保留最终上传副本检查 |
| 预览会写入 ID、首次日期、记录 | 用户取消预览后仍有本地副作用；崩溃恢复复杂 | 把身份登记视为明确操作并纳入恢复协议；界面说明副作用。日期可在确认首次发布时最终确定，需说明与旧版本语义的差别 |
| 分类每次顺序读取全部远端 Markdown | N 篇文章约 N+3 次读取请求；文章增长时等待明显 | 按仓库配置、树 SHA 和 blob SHA 缓存分类，只解析新增或修改 blob；限制并发并提供取消 |
| 快照把引用图片字节读入内存，多篇共用图片时仍会重复读；哈希和 Base64 有额外分配 | 图片多时手机内存及耗时增长 | 先按目标/来源去重；加入单图和批次容量预算、稳定哈希缓存、分阶段进度；基于低内存设备实测确定阈值 |
| 写请求全局串行，启动间隔至少一秒 | K 个变更 blob 再加 tree/commit/ref 共 K+3 个写请求；大批次存在明显时间下限 | 保留受控节流，提供进度、取消边界和可恢复状态；对限流与临时错误分类处理，写操作重试前核验远端结果 |
| 逐行 LCS 合并使用二维表，乘积超过 2,000,000 拒绝 | 两边约 1,414 行时即可触及限制，长代码文章容易遇到 | 先加完全相等/单边未变的快速路径，再考虑线性空间或成熟差异算法；基于真实语料验证内存、时间与合并正确性 |
| 首页排序直接编辑特定 JS 脚本，Fluid 功能在核心设置中 | 对当前站点很方便，但迁移其他主题成本高；UI 假定名单外排序逻辑，实际只验证了数组格式 | 长期分成 Hexo/主题适配器；排序逐步迁移到专用 JSON/YAML 数据，旧脚本保持兼容，通用 UI 不推断脚本其余语义 |
| 配置逐个输入即保存，缺少整体校验 | 中间状态可能不合法；本地记录 key 与共享 profile 的字段范围不同，路径配置切换后的体验不一致 | 草稿设置→整体校验→一次保存；规范仓库大小写、路径与空值；统一版本化配置身份并提供迁移预览 |
| `site` 设置尚无实际消费逻辑 | 用户填写后不能直接看到收益 | 接入“打开已发布文章”或部署核验；暂不实现时说明用途或隐藏该项 |
| `main.ts` 约 71.7 KB，约占源码字节数 70%，大量多操作长行 | UI、持久化、发布、恢复互相耦合，状态逻辑容易在不同入口不一致 | 先格式化，再逐步提取 StateStore、PublishPlanner、PublishTransaction、ConflictService、界面模块；统一错误类型和共享状态类型 |

图片压缩值得做，但优先级应低于上述一致性问题。目录内网站的构建后压缩处理的是公开副本，不能减少插件上传原图的流量和源码仓库体积。若插件增加压缩，应在预览前生成明确派生文件，允许检查质量、尺寸和元数据，不修改用户原图。远端孤立图片清理应独立提供引用检查、候选列表和手动确认，避免默认删除共享资源。

## 推荐的实施顺序

以下是建议里程碑，并非已完成或承诺工期。

| 阶段 | 要解决的问题 | 完成标准 |
| --- | --- | --- |
| 第一阶段：补安全与恢复缺口 | 注释/BOM、撤回事件、overlay 冲突入口、状态一致性、ID 半完成操作 | 本报告对应场景都有期望行为的回归测试；正常状态与异常状态均有明确操作出口 |
| 第二阶段：整理状态基础 | 以 ID 管理文章；重命名回退；操作 journal；同步文件完整性；配置身份和旧数据迁移 | 两设备乱序、重复同步、旧设备重回、关键步骤退出后均可安全恢复；旧版记录迁移可回滚 |
| 第三阶段：改善日常使用 | 差异预览、按篇处理、分类缓存、图片预算、进度和错误详情、Markdown 支持清单 | 用真实文章集及图片集测量桌面/手机表现；用户能定位到具体文章、字段、路径及解决动作 |
| 第四阶段：扩展与发布 | 主题适配、可选图片优化、站内链接、安装与升级验收 | 在最低支持桌面版、目标手机设备、真实同步工具和隔离远端仓库验证完整流程 |

暂不建议把“自动上传”“静默重试”“更多主题”作为近期主任务。当前手动确认有明确价值；把异常恢复补全后，才能合理扩大自动化范围。

## 建议的数据模型方向

以稳定 ID 为中心，减少依赖多个路径字典同时更新：

```ts
interface ArticleRecord {
  id: string;
  localPath: string;
  remotePath?: string;
  status: 'unpublished' | 'published' | 'withdrawn';
  baselineBlobSha?: string;
  lastPublishCommit?: string;
  publishedAt?: string;
  revision: number;
  overlay?: { base: string; merged: string; hash: string };
}
```

这是结构示意，**单一 revision 计数不能自动解决跨设备并发**。实际合并还需事件 ID、设备 ID、父版本关系和 GitHub 事实核验。适合先实现小范围的显式事件协议，不必立即引入完整 CRDT 框架。

一种可评估的进阶方案是在源码仓库增加最小发布清单，与文章进入同一次提交，使文章 ID、远端路径和发布状态有可恢复的远端依据。公开仓库中的清单不能放本地 Vault 路径、私有字段或合并全文；本地仍需 journal 应对 ref 更新结果不确定。清单也应支持冲突检测和人工接管已有文章，不能仅凭同名文件认领归属。

## 测试与文档应同步更新

- 将本次诊断脚本中的已复现行为转成修复后的期望回归测试。诊断脚本目前断言的是缺陷仍存在，不能直接作为修复验收测试。
